## The question nobody asks in the demo

Every core banking vendor will show you a happy-path transaction. The HTTP call goes out, the 200 comes back, the balance updates. Clean. But the question that separates infrastructure that works from infrastructure that works *at scale* is simpler and harder: **what does your ledger guarantee when the network partitions?**

Most demos don't cover that. Ours does.

## Double-entry is not optional

The IDMB ledger is strictly double-entry. Every debit has a matching credit. Every entry is immutable - we never update a row, we write a compensating entry. This sounds obvious, but a surprising number of modern "core banking" APIs are a single-table balance store with an audit log bolted on. That's not a ledger. That's a spreadsheet with a webhook.

Double-entry means:
- Reconciliation is always consistent by construction
- Reversals never create phantom balances
- Every balance can be reconstructed from the entry log

## API shape at high throughput

The pattern that breaks first at scale is synchronous balance reads during write operations. If your core bank answers "what is the current balance?" by summing the entry table in real time, you've already lost at 50k TPS.

The IDMB approach: **event-sourced writes, materialised balance reads**. Writes go into the entry log immediately. Balances are projected asynchronously and cached with strong consistency guarantees - the read path never blocks the write path.

The implication for integrators: if you call `GET /accounts/{id}/balance` and `POST /ledger/transfer` in the same millisecond from two threads, both calls are correct. The transfer will either complete fully or not at all (idempotency key + optimistic locking on the account), and the balance will reflect it within the consistency window you've configured (default: 50ms).

## What idempotency actually means

Every IDMB write endpoint accepts an `Idempotency-Key` header. If you send the same key twice - due to a timeout retry, a dead queue reprocessing, or a bug - the second request returns the original response without replaying the operation.

The key is stored for 48 hours. After that, it expires and a new request with the same key is treated as a fresh operation. This is the same model Stripe popularised. We copy it because it's correct.

```http
POST /v1/ledger/transfers
Idempotency-Key: txn_prod_28af91

{
  "from": "acct_northbank_001",
  "to":   "acct_northbank_002",
  "amount": { "value": 10000, "currency": "GBP" },
  "memo": "Salary payment"
}
```

## The reconciliation feed is not an afterthought

Regulators and operations teams live in reconciliation. The IDMB entry feed is a first-class API surface: paginated, filterable by account, date range and entry type, and available as a streaming webhook (one event per entry, ordered). The same feed powers our regulatory reporting module, so what your ops team sees and what your regulator sees are derived from the same immutable log.

## What to look for in any core banking API

1. Is the write acknowledged only after durability? (not after in-memory acceptance)
2. Does it use double-entry natively, or is it a balance store with audit?
3. What's the idempotency model?
4. Does the reconciliation feed derive from the same log as balances, or is it a separate system?
5. What happens to in-flight transactions during a region failover?

If the answers to 1–4 aren't in the documentation, ask them in the first sales call. The answers to these questions cost months to discover in production.
